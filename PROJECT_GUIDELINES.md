# Правила для новых проектов

Этот репозиторий — коллекция самостоятельных мини-проектов на чистых **HTML, CSS и JavaScript**, предназначенных для запуска на статическом сервере.

Каждый проект должен быть независимым, запускаться без сборки и не требовать backend.

---

## 1. Структура репозитория

```text
Collection_of_ideas/
├── PROJECT_GUIDELINES.md
├── IDEAS.md
├── README.md
├── index.html
├── projects.json
└── project_name/
    ├── index.html
    └── README.md
```

Каждый мини-проект находится в отдельной директории непосредственно в корне репозитория.

---

## 2. Обязательные файлы проекта

Минимальная структура:

```text
project_name/
├── index.html
└── README.md
```

Дополнительные файлы разрешены:

```text
project_name/
├── index.html
├── README.md
├── style.css
├── script.js
├── assets/
└── ...
```

Не создавать дополнительные файлы, если они не нужны проекту.

---

## 3. Требования к `index.html`

`index.html` должен быть самостоятельной точкой входа проекта.

Обязательные требования:

* проект должен запускаться открытием `index.html` через статический HTTP-сервер;
* не использовать backend;
* не требовать npm, bundler или build step;
* использовать только HTML, CSS и JavaScript, если иное явно не требуется задачей;
* все локальные пути должны быть относительными;
* `favicon.ico` должен подключаться относительным путём к favicon в корне репозитория;
* интерфейс должен корректно работать на desktop и mobile;
* не допускать горизонтального overflow без явной причины;
* не оставлять критические ошибки JavaScript в консоли;
* интерактивные элементы должны иметь понятное состояние `hover`, `focus`, `active`, если это применимо.

### Внешние ресурсы

Не добавлять внешние CDN, библиотеки и API без необходимости.

Если внешний ресурс используется:

1. проект должен иметь понятное состояние загрузки;
2. должна быть предусмотрена обработка ошибки;
3. по возможности должен существовать локальный fallback;
4. проект не должен ломаться полностью из-за недоступности внешнего ресурса.

Если функциональность может быть реализована нативным HTML/CSS/JS, предпочитать нативную реализацию.

---

## 4. Независимость проектов

Каждый проект должен быть максимально изолирован от остальных.

Запрещается без необходимости:

* зависеть от JavaScript другого проекта;
* подключать CSS другого проекта;
* использовать состояние другого проекта;
* требовать запуска другого проекта;
* использовать абсолютные пути к файлам конкретного проекта.

Общие ресурсы допустимы только тогда, когда это действительно оправдано архитектурой репозитория.

---

## 5. Требования к JavaScript

Предпочтительный подход:

* vanilla JavaScript;
* небольшие самостоятельные функции;
* понятные имена переменных;
* отсутствие глобального состояния без необходимости;
* обработчики событий должны корректно удаляться/не дублироваться, если проект динамически переинициализируется;
* не использовать `eval`;
* не добавлять зависимости ради простой функциональности.

Перед завершением работы проверить:

* ошибки JavaScript;
* обработку пустых/некорректных данных;
* повторное взаимодействие с UI;
* resize окна;
* mobile viewport, если интерфейс интерактивный.

---

## 6. Адаптивность

Проект должен быть usable минимум в следующих сценариях:

* desktop;
* tablet;
* mobile.

Не следует проектировать интерфейс только под один размер экрана.

Особое внимание:

* размеру интерактивных элементов;
* переполнению текста;
* viewport height;
* touch-взаимодействию;
* ориентации экрана, если она имеет значение.

---

## 7. Доступность

По возможности использовать семантический HTML.

Для интерактивных элементов:

* использовать `<button>` вместо кликабельного `<div>`;
* использовать `<a>` для навигации;
* поддерживать клавиатурное управление;
* не удалять `outline` без альтернативного focus-state;
* добавлять `aria-label`, только когда визуального текста недостаточно.

Доступность не должна усложнять проект без необходимости, но базовое управление с клавиатуры должно сохраняться.

---

## 8. `README.md`

README каждого проекта должен быть коротким, но содержательным.

Минимальный формат:

```md
# Название проекта

Краткое описание проекта в 1–3 предложениях.

## Управление

- Клавиатура: ...
- Мышь: ...
- Колесо: ...
- Touch/жесты: ...
- Дополнительные режимы: ...

## Особенности

- ...
```

Не добавлять документацию, которая не помогает понять или использовать проект.

---

## 9. Название проекта

Имя директории:

```text
snake_case
```

Требования:

* короткое;
* понятное;
* только ASCII;
* без пробелов;
* без дат и случайных идентификаторов.

Пример:

```text
particle_playground/
```

Название проекта в UI, `README.md` и `projects.json` должно быть человекочитаемым:

```text
Particle Playground
```

---

## 10. Регистрация проекта

После создания проекта необходимо обновить `projects.json`.

Новый проект считается завершённым только после выполнения обоих действий:

1. создана директория проекта;
2. проект добавлен в `projects.json`.

Не удалять и не изменять существующие записи без необходимости.

Перед добавлением проверить, что:

* `id`/путь уникален;
* путь соответствует реальной директории;
* название соответствует проекту;
* JSON остаётся валидным.

---

## 11. Производительность

Мини-проект должен загружаться быстро.

Предпочитать:

* CSS вместо изображений там, где это разумно;
* SVG вместо растровых изображений для простых графических элементов;
* системные шрифты;
* локальные небольшие ассеты;
* lazy loading для необязательных тяжёлых ресурсов.

Не добавлять:

* большие изображения без необходимости;
* тяжёлые библиотеки;
* фреймворки;
* сторонние шрифты;
* аналитические скрипты;

если задача проекта не требует этого.

---

## 12. Сетевые зависимости

Проект должен по возможности работать offline после загрузки необходимых локальных файлов.

Если проект использует сеть:

```text
loading → success
        ↘ error/fallback
```

Пользователь должен понимать, что происходит.

Не оставлять бесконечный spinner или пустой экран при ошибке сети.
